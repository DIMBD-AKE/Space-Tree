# Space Tree 성능 검증

## 회수 공간 집계 — 2026-10-09

폴더별 회수 대상은 파일시스템의 `EF_IS_PURGEABLE` 표시가 있는 파일의 할당량입니다. 단독 회수 예상은 해당 파일의 `ATTR_CMNEXT_PRIVATESIZE`만 더하며, 다른 하드 링크가 남는 파일은 0으로 취급합니다. 공유 파일을 함께 삭제했을 때의 추가 회수량까지 계산하지 않는 보수적 합계입니다. 디스크 전체 회수 예상은 Foundation의 `volumeAvailableCapacityForImportantUsage`와 현재 빈 공간의 차이이며, 특정 폴더에 배분하거나 폴더 합계에서 빼지 않습니다. 조회 실패·지원되지 않는 항목은 확인 불가로 표시합니다. [Apple 회수 대상 정의](https://developer.apple.com/documentation/foundation/urlresourcekey/ispurgeablekey), [Apple 중요 작업의 가용 공간 정의](https://developer.apple.com/documentation/foundation/urlresourcevalues/volumeavailablecapacityforimportantusage)

일반 파일마다 Foundation URL을 조회하지 않고, 기본 탐색이 끝난 폴더의 메타데이터를 `getattrlistbulk`로 묶어 읽습니다. 일반 파일이 없는 폴더는 이 조회를 생략합니다. 추가 블록 조회는 확인된 회수 대상만 수행하며, 일반 파일의 회수 메타데이터는 공유하는 빈 객체 하나를 사용합니다. `sample` 5초 프로파일에서 추가 비용은 주로 커널의 벌크 속성 조회에 있었습니다.

Apple M4, 16 GiB RAM, macOS 26.5.2, 로컬 서명 Release 앱에서 `/System/Volumes/Data`를 작업자 4개로 한 번씩 분석했습니다.

| 전체 항목 | 2,787,875 | 2,787,920 |
| 파일 | 2,437,948 | 2,438,062 |
| 스냅샷 보관 시점 RSS | 374.16 MB | 397.51 MB |

추가 메타데이터 조회를 포함한 분석은 약 4.60초(23.4%) 늘었습니다. 실제 사용 중인 파일시스템이므로 파일 수가 변했고 캐시·다른 앱·메모리 압력을 통제하지 않았습니다. 이 비율은 참고값이며 고정 데이터셋의 성능 보장이 아닙니다. GUI 화면 그리기 비용은 포함하지 않습니다. [기존 결과](benchmark-recovery-before.json), [최종 결과](benchmark-recovery-after.json)

최종 결과에서 확인된 회수 대상은 153개, 할당량과 단독 회수 예상 모두 204,824,576바이트였습니다. Users는 48개·204,394,496바이트, System은 105개·430,080바이트이며 회수 속성·단독 블록 조회 실패는 0개였습니다. 읽지 못한 시스템 영역 217개는 이 합계에 포함되지 않습니다. 같은 시점 디스크 전체 회수 예상은 1,532,055,616바이트였습니다. 앞선 조사에서는 약 170.78 GB를 반환했으나 그 차이만큼 실제 사용 공간이 감소하지는 않았습니다. 시스템 추정치 변동을 파일 삭제량으로 해석하지 않습니다.

기존 검증을 포함해 테스트 16개 중 15개 통과, 마운트된 시뮬레이터 볼륨이 필요한 1개는 환경 조건으로 생략했습니다. 임시 파일에 실제 회수 플래그를 설정하여 직렬·병렬 집계, 하드 링크, 폴더 진입, 플래그 해제 후 FSEvents 자동 갱신을 검증했습니다. 900×600 오프스크린 렌더링으로 배치를 확인했고 로컬 앱의 엄격한 서명 검증을 통과했습니다. 실제 앱 창 조작은 컴퓨터 UI 연결 오류로 확인하지 못했습니다.

## 디스크 전체 탐색 추가 개선

매킨토시 HD의 Data 전체 분석에서, 기존 두 단계까지만 작업을 나누는 방식은 `Users/deurim`처럼 큰 트리를 한 작업자가 끝까지 맡게 했습니다. 실제 GUI 5초 프로파일에서 세 작업자는 조건 대기, 한 작업자는 `getattrlistbulk`를 실행했습니다. 또한 트리는 작업 완료 시에만 전달됐고 진행 항목 수 전달이 트리 전달의 타이머를 공유했습니다. 새로 고침은 기존 루트가 있다는 이유로 부분 결과 전달 자체가 꺼져 있었습니다.

유휴 작업자가 생기면 탐색 중 발견한 깊은 폴더도 즉시 분배하도록 변경했습니다. 작업자는 최대 4개이며 대기 URL은 소비 후 정리합니다. 진행 중인 디렉터리의 완료된 자식을 공유하고 열린 조상 경로만 복사해 약 0.5초를 목표로 부분 결과를 전달합니다. 진행 항목 수와 트리 전달의 타이머를 분리하고 콜백을 직렬화해 오래된 결과가 새 결과를 덮지 않게 했습니다. 전체 재분석에도 이 전달을 적용하며, 미완료 용량에는 `…`가 표시됩니다. 사용자가 기다리는 전체 분석은 `userInitiated`, 자동 증분 추적은 `utility` 우선순위를 사용합니다.

중간 구현의 프로파일에서는 트리를 합칠 때 Foundation URL의 디렉터리 추론이 반복적으로 `lstat`를 호출하고 다른 작업자를 막는 것을 확인했습니다. 이 구현은 채택하지 않았습니다. 최종 트리 병합은 문자열 경로만 조합하며 파일시스템을 조회하지 않습니다. 새 작업을 시작할 때 조상 경로의 실제 디렉터리·심볼릭 링크 검증은 유지합니다.

| 측정 | 개선 전 | 개선 후 | 비율 |
| --- | ---: | ---: | ---: |
| 동일한 깊은 10만 파일 트리, 5회 중앙값 | 228.90 ms | 67.67 ms | 3.38배 |
| 동일 트리 p95 | 261.18 ms | 84.38 ms | 3.10배 |
| 실제 Data 볼륨, 전체 분석 한 번 | 84.62초 | 33.37초 | 참고 측정 2.54배 |

고정 트리는 100개 폴더의 10만 희소 파일을 `Users/person/Desktop/projects/fixture` 아래에 둬 디스크 전체 탐색의 깊은 구조를 재현했습니다. 두 실행 모두 파일 100,000개, 전체 항목 100,106개, 논리 크기 199,974,459,938바이트, 할당 크기 0바이트로 일치했습니다. 5회는 OS 메타데이터 캐시가 적용된 비교이며 디스크 캐시를 비운 측정이 아닙니다. 네이티브 측정 구간 최고 RSS는 55.05 → 56.34 MB였습니다. [고정 트리 개선 전](benchmark-deep-before.json), [개선 후](benchmark-deep-after.json)

실제 Data 비교에서는 파일 수가 2,787,412 → 2,803,006개로 변했고 논리 크기도 약 2.34 GB 증가했습니다. 다른 앱의 동작·메모리 압력·캐시를 통제하지 않아 비율 전체를 코드 효과로 해석하지 않습니다. 개선 후 실행은 GUI처럼 부분 결과를 구성하고 관찰하는 비용도 포함하며 화면 그리기는 포함하지 않습니다. 두 실행 모두 접근 불가 항목 216개와 별도 마운트 볼륨 5개를 기록했습니다. [실제 볼륨 개선 전](benchmark-volume-before.json), [중간 결과를 포함한 개선 후](benchmark-volume-streaming.json)

개선 후 61개 스냅샷을 기록했습니다. 첫 용량이 있는 미완료 결과는 522 ms에 전달됐고 간격 중앙값은 511 ms, 최대는 2,467 ms였습니다. 파일시스템 조회가 막히면 0.5초보다 늦게 전달될 수 있습니다. `Users`의 용량은 분석 도중 53번, `Applications`는 14번 변했습니다. 마지막 스냅샷의 대기 폴더 수는 0입니다.

전체 Data 약 280만 파일을 유지한 GUI 프로파일에서는 physical footprint 약 814 MB, 최고 약 947 MB가 관측됐습니다. 이전 홈 폴더 약 213만 파일의 관측치와 범위가 다르며 메모리 압력·스냅샷·프레임워크가 포함됩니다. 모든 항목을 메모리에 유지하므로 트리 크기에 비례하는 비용은 남습니다. 네이티브 목록의 가상화와 트리맵 1,200개 셀 제한은 유지합니다. [전체 디스크 프로파일 집계](profile-volume-summary.json)

이미 접근 불가로 표시된 폴더의 이벤트가 같은 변경 묶음에 포함되면 다른 읽을 수 있는 폴더의 갱신까지 실패하던 경우도 재현하고 수정했습니다. 알려진 보호 폴더는 경고를 유지하면서 다른 변경을 반영하고, 이후 읽기 권한이 생기면 다시 분석합니다. 이전에 읽을 수 있던 폴더가 갑자기 읽히지 않는 경우의 오류·재시도 처리는 유지합니다.

최종 테스트 14개가 모두 통과했습니다. 새 검증은 깊은 폴더의 미완료 용량 전달과 그 도중 취소, 전체 새로 고침의 부분 결과 전달, 보호 폴더와 읽을 수 있는 폴더의 같은 묶음 갱신 및 권한 복구를 다룹니다. 최신 서명된 GUI에서 Data 전체 탐색을 실행해 미완료 용량·목록이 변하는 것, 최종 약 280만 파일 집계 및 이후 실제 파일 변경 반영을 확인했습니다. 엄격한 서명 검증도 통과했습니다. 측정용 임시 트리는 제거했으며 기존 사용자 파일을 변경하지 않았습니다.

## 이전 개선 결과

초기 분석은 최대 4개 작업자가 실행하며 처음 두 단계의 폴더를 나눕니다. 기존 `fts` 일괄 메타데이터 조회를 유지하고 파일 내용은 읽지 않습니다. 전체 분석이 끝나기 전에도 부분 결과로 탐색할 수 있으며 미완료 합계와 폴더를 표시합니다. GUI 스캔은 utility 큐에서 조율하고 진행 상태와 부분 결과 전달은 약 150 ms 간격으로 제한합니다.

같은 10만 파일 트리를 직렬과 병렬로 각각 5회 측정했습니다. 최신 생성기는 데이터 기록 없이 희소 파일 길이만 설정합니다. 두 실행의 파일 수 100,000개, 전체 항목 100,101개, 논리 크기 199,974,459,938바이트, 할당 크기 0바이트가 일치했습니다. 파일별 블록 합계가 0이어도 디렉터리와 APFS 메타데이터는 디스크를 사용합니다. 아래 수치는 OS 메타데이터 캐시가 적용된 반복 스캔이며 캐시를 비운 콜드 디스크 측정이 아닙니다.

[홈 직렬](benchmark-home-serial.json), [홈 병렬](benchmark-home-parallel.json)

최신 실행의 `/Applications/Xcode.app` 반복 스캔을 macOS `sample`로 5초 기록했습니다. 4개 스캔 작업자가 확인됐고 최하위 호출 표본은 `getattrlistbulk` 3,305개, `__open_nocancel` 1,009개, 조건 대기 `__psynch_cvwait` 12,034개였습니다. 대기는 폴더별 작업량 차이도 포함하며 이 표본은 CPU 사용률이나 벽시계 시간 비율이 아닙니다. 프로파일러를 붙인 시간은 벤치마크에서 제외했습니다. Instruments의 추가 launch 기록은 앱 진입 전 dyld에서 멈춰 채택하지 않았고 해당 측정 프로세스는 종료했습니다. [최신 프로파일 집계](profile-parallel-summary.json); 원본은 `.build/parallel-native-sample.txt`입니다.

11개 테스트가 모두 통과했습니다(3.126초). 기존 검증에 직렬/병렬 합계 일치·부분 결과·실행 중 취소, 다른 마운트 볼륨 제외, Data 볼륨 FSEvents 경로 정규화, 첫 권한 안내를 추가했습니다. Data 볼륨은 실제 이벤트 경로가 `/private` 같은 별칭으로 전달되어 무시되던 실패를 재현한 뒤 수정했습니다. 사용자가 전체 디스크 접근을 허용한 후 최신 앱 재실행 시 안내가 반복되지 않고 휴지통이 경고 없이 열리는 것을 확인했습니다. 휴지통은 현재 비어 있습니다. 경로 오른쪽 Finder 버튼 하나와 하단 중복 정보 삭제, 분석 중 부분 결과 표시도 실제 화면에서 확인했습니다. 최신 번들의 엄격한 서명 검증을 통과했습니다.

## 저장 공간 차이 조사

앱에 저장되어 있던 분석 루트는 `/Users/deurim`이었습니다. 홈 폴더의 파일/할당 합계를 설정의 디스크 전체 사용량과 직접 비교하면 홈 밖의 Applications·Library·private 등이 빠집니다. 새 `디스크` 선택은 `/System/Volumes/Data`를 분석하고 다른 마운트 볼륨을 중복 합산하지 않습니다. `디스크 전체 사용` 카드는 선택 폴더 합계와 별도로 `statfs`의 전체 용량 − 사용 가능한 공간을 표시합니다. 설정 앱의 카테고리 분류·회수 가능 공간 처리와 정확히 같은 계산을 보장하지 않습니다.

조사 초기 APFS 컨테이너 사용량은 465.47 GB였습니다. Data 428.74 GB 외에 System·Preboot·Recovery·VM 등이 약 36.57 GB를 사용했습니다. 같은 시기 `du -x`로 읽힌 Data 할당 합계는 379.55 GB였고 보호된 경로 216개에서 접근 오류가 발생했습니다. 약 49.19 GB 차이를 특정 폴더 하나의 크기로 확정할 수는 없습니다. 읽을 수 없는 영역 외에도 APFS 메타데이터, 공유 블록, 하드 링크 계산 방식 등으로 파일별 합계가 볼륨 사용량과 다릅니다. 전체 디스크 접근은 일반 파일 접근 제한을 줄이지만 시스템 보호와 다른 사용자의 파일 권한까지 해제하지 않습니다.

`.colima`는 이미 삭제되어 있었고 휴지통도 비어 있었습니다. 이전 Colima 측정은 논리 크기 128.90 GB, 할당 크기 3.02 GB였으므로 삭제가 논리 크기만큼 공간을 돌려주지는 않습니다. 조사 시 Time Machine 로컬 스냅샷과 Data 볼륨 APFS 스냅샷은 없었습니다. 이 Mac의 차이를 스냅샷 때문이라고 판정할 근거는 없습니다.

조사 중 설정의 사용량은 479.71 → 484.01 GB로 변했고 VM 볼륨도 10.74 → 19.33 GB로 증가했습니다. 측정용으로 남겨 두었던 임시 fixture만 정리했고 사용자 파일·휴지통·스냅샷은 삭제하지 않았습니다. 19:43 KST의 정리 후 기록은 전체 456.15 GB, Data 418.35 GB, VM 11.81 GB입니다. 이후 앱 화면의 전체 사용은 약 457.56 GB였습니다. 실시간 파일 변경·스왑·저장 공간 분류 갱신이 겹치므로 변화 전부를 Colima나 단일 원인으로 단정하지 않습니다. [볼륨 기록](storage-audit.json)

macOS의 시스템 데이터에는 로그·캐시·가상 메모리·앱 지원 파일 등 다른 분류에 포함되지 않는 데이터가 들어가며 크기는 변합니다. Colima의 카테고리는 파일 위치와 macOS 분류 결과에 따라 달라집니다. [Apple 저장 공간 안내](https://support.apple.com/ko-kr/guide/mac-help/syspf5a64aa6/mac), [Apple APFS 설명](https://developer.apple.com/documentation/foundation/about-apple-file-system), [Apple 전체 디스크 접근 설명](https://developer.apple.com/forums/thread/124895)

아래는 병렬 개선 전의 기록입니다. 생성 트리 조건이 최신 측정과 달라 수치를 직접 비교하지 않습니다.

## 조건

생성 트리는 100개 폴더에 5만/10만 파일을 분산합니다. 파일 길이는 희소 파일로 설정하고 일부에만 4 KiB를 기록합니다. 파일 내용 전송이 아닌 메타데이터 탐색을 측정합니다. 첫 스캔은 생성 직후이고, 이후 5회는 OS 메타데이터 캐시가 적용됩니다. 콜드 디스크 벤치마크가 아닙니다.

실제 트리는 `/Applications/Xcode.app`입니다. 첫 실행의 캐시 상태는 통제하지 않았습니다. 다른 앱과 홈 폴더 자동 추적이 함께 실행된 환경으로, I/O 및 메모리 압력에 따라 결과가 달라집니다. p95는 5회 측정의 상위 표본이므로 장기 지연 분포를 대표하지 않습니다.

## 프로파일링과 적용한 최적화

Instruments Time Profiler로 반복된 10만 파일 스캔을 12초 기록했습니다. 스캔 관련 CPU 표본 8,674개 중 8,155개(94.02%)의 최하위 호출은 `getattrlistbulk`였습니다. `fts_read`가 OS의 일괄 메타데이터 조회를 사용하며, 주요 비용은 이 조회에 집중됐습니다. 표본 비율은 벽시계 시간 비율이 아닙니다. 프로파일러를 붙인 실행 시간은 위 벤치마크에 사용하지 않았습니다. [집계](profile-summary.json)

파일 내용은 읽지 않고 `fts` 메타데이터만 조회합니다. 파일별 전체 경로를 중복 저장하지 않으며 이름과 자식 트리를 유지합니다. 스캔은 단일 utility 큐에서 실행하고 취소 및 오래된 결과 폐기를 지원합니다. FSEvents를 모아 변경 하위 트리만 다시 읽고 나머지 노드를 공유합니다. 트리맵 계산은 캐시하며 최대 1,200개 셀을 그립니다. 전체 항목은 네이티브 NSTableView로 표시하고 검색 입력은 150 ms 모읍니다. 자동 추적에는 주기적 폴링을 사용하지 않습니다.

홈 폴더를 추적하는 GUI의 별도 5초 `sample`에서 메인 스레드 표본의 약 97.4%는 이벤트 대기였습니다. 새 빌드의 10초 CPU 측정에서는 한 코어 대비 약 0.68%, RSS는 64.09→88.95 MB였습니다. 파일 변경과 사용자 조작을 통제하지 않은 추적 중 측정이며, 순수 유휴 CPU 보증값은 아닙니다. [원본](gui-cpu.json)

## 동작 검증

`swift test` 7개 테스트가 모두 통과했습니다(약 2.9초). 합계와 증분 결과, 숨김 파일·패키지·희소 파일·권한 오류·링크 순환·취소, 트리맵 면적 및 셀 제한, 접근성 버튼, 실제 FSEvents 생성·수정·이름 변경·삭제·루트 이동·루트 전환·추적 재개를 확인했습니다.

최종 리뷰에서 발견한 실패한 갱신 경로 보존과 조상 폴더의 심볼릭 링크 교체 문제는 실패를 재현하는 테스트를 먼저 확인한 뒤 수정했습니다. 오래된 목록 항목으로 진입하는 경로도 차단했습니다. 실제 앱에서 폴더 선택, 트리맵 진입, 할당 크기 전환 및 Finder 버튼 하나만 남은 상태를 확인했습니다. 앱 번들의 `codesign --verify --deep --strict`도 통과했습니다.
